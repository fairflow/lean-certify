## A. Provers, disprovers, deciders (`LeanCertify/Decider.lean`)

An `Engine` (v0.1) bundles one producer with both certifiers.  A decider
separates the two directions, so that the fastest tool on each side can be
used, and adds fallback pairs.

```lean
/-- A prover: an untrusted producer of certificates for `Holds`, and the
certifier that judges them.  `none` means "not found within the budget". -/
structure Prover (Spec : Type) (Holds : Spec → Prop) where
  name : String
  Cert : Type
  certifier : Certifier Spec Cert Holds
  produce : Spec → Nat → Option Cert

/-- A disprover: the same for `Holds s → False`. -/
structure Disprover (Spec : Type) (Holds : Spec → Prop) where
  name : String
  RCert : Type
  certifier : Certifier Spec RCert (fun s => Holds s → False)
  produce : Spec → Nat → Option RCert

/-- A decider: a prover and a disprover, then fallback pairs in order.  To
fall back on one side only, repeat the other side's tool in the pair. -/
structure Decider (Spec : Type) (Holds : Spec → Prop) where
  prover : Prover Spec Holds
  disprover : Disprover Spec Holds
  fallback : List (Prover Spec Holds × Disprover Spec Holds) := []

/-- A decided case, with the evidence and the tool that found it. -/
inductive Decision (Holds : Spec → Prop) (s : Spec) where
  | yes (h : Holds s) (tool : String)
  | no (h : Holds s → False) (tool : String)
  | flag (report : String)          -- every pair exhausted its budget (R5)

def Prover.ofEngine (E : Engine Spec Cert RCert Holds) (name : String) : Prover Spec Holds
def Disprover.ofEngine (E : Engine Spec Cert RCert Holds) (name : String) : Disprover Spec Holds
```

**Run semantics** (`Decider.run : Decider Spec Holds → RunConfig → Spec → IO (Decision Holds s)`):
the pairs in order; within a pair the prover and the disprover race in two
threads (or run one after the other, `mode := .sequential`); a produced
certificate is checked by its certifier's compiled `check`, and the first
one that passes decides; a budget that runs out is raised (`flagReruns`,
`budgetFactor`) and then the next pair is tried; every skip and cap is in
the report.  The `Decision` carries `Holds s` obtained from `sound` and the
compiled check; the kernel-checked fact still goes through `Certifier.verdict`
(step 6), unchanged.

**Theorem** (the only one; everything else is data and IO):

```lean
theorem Decider.decide_sound (D : Decider Spec Holds) (s : Spec) :
    D.decideWith s outcome = .yes h tool → Holds s     -- by construction of `yes`
```

Nothing about completeness: a decider never claims more than its
certificates.

## B. Configuration: three options against decision 12

Decision 12 of the outline (2026-10-09): settings live in one per-project
Lean file, typed and checked at elaboration; JSON is only ever generated
from it.  The request now is a simple configuration that someone who does
not know Lean can use.  Three ways, OPEN:

1. **Keep decision 12, add a template.**  The decider is a Lean constant in
   the project's config file; a commented template shows the four lines to
   edit (prover, disprover, fallback, run settings), each tool named by the
   project's registered name.  Run-time knobs (`deadlineSec`, `budget`,
   `mode`) also accepted as command-line flags, which override the file for
   one run and never feed a lint or a gate.  *Recommended*: one source of
   truth stays, names are checked at elaboration, and the template carries
   the documentation.
2. **JSON for the decider only.**  `decider.json` names the tools from the
   project's registry and the run settings; the compiled runner reads it.
   The lints and gates (axiom list, chunk size, …) stay in Lean.  Supersedes
   decision 12 for run-time settings only; a misspelt tool name is caught at
   run time, not at elaboration.
3. **Command line only.**  `certify-decide --prover subtab --disprover subtab
   --fallback frjw,enum --deadline 120 "<spec>"`.  Simplest to start;
   nothing to commit, so no record of what was run.

In every option a project supplies, once, in Lean: the registry of its
tools (`List (String × …)`) and a parser `String → Except String Spec`.
`Certify.Cli.main registry parse` is the generic executable.

```lean
structure RunConfig where
  mode : Mode := .race              -- .race | .sequential
  budget : Nat := 1000              -- handed to `produce`; raised on a flag
  flagReruns : Nat := 2             -- R5, default from Harness.config
  budgetFactor : Nat := 4           -- R5
  deadlineSec : Nat := 600          -- R7, per run
  deriving Repr, ToJson, FromJson
```

### B.1 in full (approved 2026-10-15: option 1)

**The Lean settings file** (one per project, e.g. `Harness/Settings.lean`).
The project registers its tools once; a user edits only the lines marked
EDIT.

```lean
import LeanCertify
import MyProject.Tools          -- defines the tools named below

/-! # Lean certify settings for this project

Edit only the lines marked EDIT.  A tool is named by a string from
`Harness.tools`; a misspelt name is an error when this file is compiled.
To fall back on one side only, repeat the other side's tool in the pair. -/

/-- The tools this project offers, by name (written once, by the project). -/
def Harness.tools : Harness.Registry PLLFormula Holds :=
  [ .pair "subtab" SubTab.prover SubTab.disprover,
    .prover "frjw" FRJW.prover,
    .disprover "enum" Enum.disprover ]

/-- Project-wide gate settings (v0.1; unchanged). -/
def Harness.config : Harness.Config := { chunkSize := some 8 }

/-- The decider. -/
def Harness.decider : Harness.DeciderConfig where
  prover    := "subtab"                    -- EDIT
  disprover := "subtab"                    -- EDIT
  fallback  := [("frjw", "enum")]          -- EDIT: pairs, tried in order
  run       := { mode := .race,            -- EDIT: .race | .sequential
                 budget := 1000,
                 deadlineSec := 120 }

#certify_decider Harness.decider           -- checks every name against Harness.tools
```

**The JSON, generated from it** (`lake exe certify-json`, or
`#eval IO.println (toJson Harness.decider).pretty`), for tools that are not
Lean.  It is output, never read back as a source (decision 12):

```json
{
  "prover": "subtab",
  "disprover": "subtab",
  "fallback": [["frjw", "enum"]],
  "run": {
    "mode": "race",
    "budget": 1000,
    "flagReruns": 2,
    "budgetFactor": 4,
    "deadlineSec": 120
  }
}
```

**Command-line overrides for one run** (never feed a lint or a gate):
`certify-decide --deadline 300 --mode sequential "<spec>"`.

```lean
structure DeciderConfig where

  disprover : String

  run : RunConfig := {}
```

### Backward compatibility

v0.3 adds a module (`LeanCertify/Decider.lean`), new structures
(`Prover`, `Disprover`, `Decider`, `Decision`, `RunConfig`, `DeciderConfig`,
`Registry`) and one command (`#certify_decider`).  It changes no existing
signature: `Certifier`, `Verdict`, `Engine`, `Refinement`, `Harness.Config`
and the `@[harness]` attribute stay as in 0.2.1, and `Harness.Config` gains no
field (so its JSON is unchanged).  A file written against 0.1.x or 0.2.x
compiles unchanged against 0.3.0; nothing is recoded.  The decider is
opt-in: an existing `Engine` becomes a prover and a disprover through
`Prover.ofEngine` / `Disprover.ofEngine`, without touching the engine.

The one break in the library's history so far is 0.2.0 (the shape of
`Refinement`, with its migration note); it does not recur in 0.3.
